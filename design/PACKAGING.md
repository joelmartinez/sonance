# Sonance — packaging (P1, 2026-11-11)

This record says what the package is, what is inside it, and how versions are handled, so the publish gate is a decision and not a scramble. The library was made package ready without being published: publishing happens only on the owner's explicit word, in an interactive session, with the owner's npm credentials.

The package is @codecube/sonance, an ES module package (type module) whose runtime is plain JavaScript in src/ with no build step, so what a consumer installs is exactly the code in this repo. Its one dependency is tone at ^15.1.22, installed by the consumer's package manager from Sonance's own declaration. Node 18 or newer is the stated floor for tooling, and the library itself runs in browsers with Web Audio support; creating real sounds needs a browser audio context, while the engine object, the MIDI helpers, and the scene presets also work in Node.

The exports map in package.json is the public contract. The root entry (@codecube/sonance) points at src/index.js with types at src/index.d.ts, and @codecube/sonance/package.json is also exported so tooling can read the manifest. The older main and module fields stay, pointing at the same entry, and the top-level types field names the same declaration file, for resolvers that do not read exports maps. There are no subpath exports: every public name lives on the root entry, exactly as src/index.js defines it. Imports inside the package use relative paths with .js extensions throughout, so nothing depends on this map for the library's own files, and consumer code that imports the package name today against a local checkout will import the published package unchanged after the flip.

The type declarations in src/index.d.ts are hand-written against the runtime, not generated, because the sources are plain JavaScript. They cover every export of the entry (the SonanceEngine, Sound, Soundtrack, Channel, and Instrument classes, the MidiUtils helpers and constants, loadSoundtrack, the SonanceSceneManager statics, the Tone re-export, and the default Sonance object with createEngine) plus the shapes consumers actually touch: engine, sound, instrument, channel, and soundtrack options, note events, effect descriptors, soundtrack and scene definitions, and the five-method contract an injected modulation system must satisfy. Tone.js objects that cross the API (nodes and modulation targets) are typed structurally or as unknown on purpose, so consumers are not forced into a Tone.js type dependency beyond the package they already install at runtime. The declarations were verified two ways for P1: a runtime check that every name the declarations promise exists on the real module with the right kind, and a TypeScript compile, under strict mode, of a small consumer that imports the package and uses the headline APIs.

What ships is set by the files allowlist in package.json, and the allowlist is the whole story because npm always adds package.json, the README, and the license on its own. The tarball carries src/ (the twelve runtime files, the demo soundtrack JSON, and the declarations) and CHANGELOG.md: 17 files in total, listed in PROGRESS.md for the P1 session. It deliberately leaves out the examples, the tests, the design and extraction records, and the progress and roadmap working files, because none of that is something a consumer runs; the examples still prove themselves against the packed package, since the P1 session installed the tarball into a clean folder, pointed the examples' import maps at the installed package, and ran both pages headlessly with no errors. The same clean folder ran the README quickstart code, extracted word for word from the packed README, in a headless browser: the engine started, the sound and the looping soundtrack were created, and the four preset names printed, with no console errors and no failed requests.

Version discipline is simple and is stated in CHANGELOG.md where consumers will see it: Semantic Versioning, the version field in package.json is the single source of truth, every change that will ship is written into the changelog's Unreleased section in the same commit that makes it, a release renames that section to the new version with its date before publishing, and breaking changes to the public exports are called out in the changelog in plain words. The version prepared by P1 is 0.1.0, the first package-ready build; it stays unpublished until the gate clears, and the post-publish consumer flip (roadmap C1) changes only each consumer's dependency line, never its imports.
