# Sonance — decoupling plan (D1 audit, 2026-11-11)

This plan maps every coupling between Sonance and its original host, the Static-Site-Generator (SSG) that runs codecube.net, and gives D2 an ordered fix list. Every claim below was verified by reading the actual files in this repo on 2026-11-11 (`src/`, `tests/`, `package.json`, and the evidence copies in `extraction-notes/`), not from the extraction notes alone. The headline finding is reassuring: nine of the twelve source files are already clean, and almost every coupling lives in exactly two files — `src/SonanceEngine.js` and `src/index.js` — plus the two extracted tests. One live check confirms the state plainly: importing `src/index.js` in Node today fails, first on the uninstalled `tone` package and, once that is installed, on the missing `../modulation/index.js`, so the package's declared entry point cannot be imported at all by a standalone consumer right now. That is the problem D2 fixes.

## What is already clean

`Channel.js`, `EffectChain.js`, `Instrument.js`, `MidiUtils.js`, `Sound.js`, `Soundtrack.js`, and `variation.js` import nothing outside this repo except `tone` (covered as S1 below), every relative import already carries its `.js` extension, and none of them touches `window`, `document`, `localStorage`, `fetch`, or any host path — so the extensionless-import problem Photonic's D1 had to fix first does not exist here. `MidiUtils.js` and `variation.js` have no imports at all. There are no fetch calls, no audio file URLs, and no asset paths anywhere in the tree; all sound is synthesized, and `src/soundtracks/ambient-demo.json` is pure note and effect data with no URLs in it. The `modulationTargets` objects that `Sound`, `Channel`, and `Instrument` build are plain in-repo data structures describing which parameters a modulation binding may drive; they import nothing from the Modulation workstream and are the seam a modulation system consumes, not a coupling, so D2 leaves them exactly as they are. The AudioContext itself comes from Tone and `SonanceEngine.start()` documents that it must be called from a user gesture, which is a Web Audio platform rule any consumer lives with, not host knowledge. The `extraction-notes/` folder, including the host `package.json`, webpack, jest, and babel copies kept there, is evidence and documentation only; `package.json`'s `files` list already limits the published set to `src/` (plus the always-included README, LICENSE, and package.json, as the E2 pack dry run showed), so nothing in that folder is a runtime coupling and D2 leaves it in place.

## The central question, answered: what happens to Modulation

The Modulation workstream is the one real design decision in this plan, so it is settled here rather than left to D2. The facts, verified in the files: `SonanceEngine.js` imports `ModulationSystem` from `../modulation/index.js` and constructs one by default when the caller does not pass `options.modulation`; the engine's entire use of it is four thin wrapper methods (`createModulator`, `getModulator`, `bindModulator`, `updateModulation`), one `dispose()` call, and the `modulation` getter — no Sound, Soundtrack, Channel, or Instrument code path touches it. `src/index.js` imports nine names from the same place (`ModulationSystem`, `Modulator`, `ModulationBinding`, `clamp`, `createPhotonicFrameContext`, `distance3D`, `lerp`, `normalizeToUnit`, `readPath`) and re-exports all of them, including inside a `Modulation` namespace object; a grep over the rest of `src/` confirms none of those nine names is used anywhere else in the library, so the re-exports are pure surface with no internal consumer. The Modulation sources were not extracted in E1 and do not exist in this repo, and one of the re-exported names, `createPhotonicFrameContext`, shows the workstream is shared with Photonic rather than owned by Sonance — which is also why Photonic's own decoupling dropped its Modulation re-exports instead of carrying them.

Three approaches were considered. Declaring Modulation as a dependency fails because there is nothing to declare: no `@codecube/modulation` package or repo exists, so D2 would block indefinitely on a workstream nobody has scheduled. Internalizing the Modulation sources fails for this step because they were never extracted, pulling them in is a new extraction with its own inventory work, and it would drag the Photonic-facing frame-context coupling into a library whose own code does not need it. Severing is therefore the plan, and the code already contains the seam that makes it clean: the engine constructor accepts `options.modulation`. D2 severs the import, makes modulation an optional injected system (S2), and drops the nine re-exports (S3). A caller who has a modulation system passes it in and gets the exact behaviour the host had; a caller who does not gets a fully working engine for Sounds and Soundtracks, with the modulation methods failing loudly and clearly instead of the import failing silently at load time. If Joel later wants Modulation as its own extracted library, that is a new roadmap item with its own extraction, and Sonance's injection seam is already the right shape to consume it. This decision is the one place D1 makes a product-level call; it is flagged in the D1 check-in so Joel can redirect it before D2 runs if he disagrees.

## The couplings, in the order D2 should fix them

### S1 — The tone dependency: declare it properly (already declared; verify and keep)

Seven files import `tone` as `import * as Tone from 'tone'` (`Channel.js`, `EffectChain.js`, `Instrument.js`, `Sound.js`, `SonanceEngine.js`, `Soundtrack.js`, and `index.js`), and `index.js` re-exports it as `Sonance.Tone` for consumers. This is a true external dependency, not a host coupling in disguise: the host's `package.json` pinned it at `^15.1.22`, and E2 already carried exactly that range into this repo's `package.json` as a regular dependency. The classification is dependency, not peer dependency, and the difference from Photonic's `three` peer is deliberate: Sonance's classes construct and own Tone objects directly throughout, so a consumer should get a tested Tone version with the library rather than being asked to supply one. Fix approach: declare (done in E2) — D2 keeps the `^15.1.22` range, keeps the `Tone` re-export as public surface, and proves the declaration is sufficient by having the standalone test below install Tone from this declaration alone. No code changes belong to this item.

### S2 — SonanceEngine.js imports ModulationSystem across the tree and constructs one by default: sever, keep the injection seam

`src/SonanceEngine.js` line 26 imports `ModulationSystem` from `../modulation/index.js`, a path that resolves nowhere in this repo, and the constructor (line 33) builds `options.modulation ?? new ModulationSystem()`, so merely constructing an engine — the first thing any consumer does — would throw even if the import were shimmed. This is the deepest coupling in the library because it sits in the engine's core lifecycle, including `dispose()`, which calls `this._modulation.dispose()` unconditionally. Fix approach: sever. D2 removes the cross-tree import, stores `options.modulation ?? null`, and defines the no-modulation behaviour explicitly: the `modulation` getter returns the injected system or `null`; `createModulator`, `getModulator`, `bindModulator`, and `updateModulation` throw a clear error naming the missing piece (for example, "Sonance: no modulation system — pass one as options.modulation to use modulation") when no system was injected, rather than failing with an undefined-property crash; and `dispose()` disposes the modulation system only when one exists. The injected-system contract is documented in the code header and the README as the five methods the engine actually calls — `createModulator(id, options)`, `getModulator(id)`, `bind(options)`, `update(deltaTime, context)`, and `dispose()` — so any future Modulation library, or a small hand-rolled system, can be plugged in without Sonance importing it. One knock-on effect D2 must handle in the same step: `SonanceSceneManager.applyScene` calls `engine.createModulator` for every modulator in a scene definition, and all four built-in presets define modulators, so applying a preset to a modulation-free engine would hit the new error on its first line. `applyScene` therefore skips the modulators section with a `console.warn` naming what was skipped when the engine has no modulation system, and still applies the scene's sounds and soundtracks; with a system injected, its behaviour is unchanged.

### S3 — src/index.js re-exports nine Modulation names as public surface: sever (drop the re-exports)

`src/index.js` lines 18–28 import `ModulationSystem`, `Modulator`, `ModulationBinding`, `clamp`, `createPhotonicFrameContext`, `distance3D`, `lerp`, `normalizeToUnit`, and `readPath` from `../modulation/index.js`, builds a `Modulation` namespace object from them, and exposes them both on the `Sonance` object and as named ES exports. Because the import sits at the top of the package's entry point, this is the coupling that makes the whole package unimportable standalone, ahead of every other problem. As established in the central-question section, nothing else in the library uses any of these names — the small math helpers among them (`clamp`, `lerp`, `distance3D`, `normalizeToUnit`, `readPath`) have no in-repo consumer to internalize them for, and Photonic's decoupling reached the same conclusion for its own Modulation re-exports. Fix approach: sever — D2 deletes the import, the `Modulation` namespace object, and all nine names from both the `Sonance` object and the named exports. This is a deliberate public-surface break against the host-era bundle, recorded here so it is a decision rather than a surprise: host consumers that used `window.Sonance.Modulation` or `window.Sonance.createPhotonicFrameContext` are the two photonics examples, which are unsupported until X1 (S9) and will be rebuilt against the decoupled surface there. The remaining exports — `SonanceEngine`, `Sound`, `Soundtrack`, `Channel`, `Instrument`, `MidiUtils`, `loadSoundtrack`, `SonanceSceneManager`, `Tone`, the `createEngine` factory, and the default export — are all backed by files in this repo and stay.

### S4 — The window.Sonance global: sever from the library; the global belongs to a host page, not a package

`src/index.js` sets `window.Sonance = Sonance` whenever `window` exists (lines 72–74, guarded, so importing in Node does not crash), and its header comment describes the file as "Exposed as window.Sonance when bundled as a standalone script" — the consumption model of the host's webpack bundle, not of an ES module package. Both known host consumers lean on this global instead of importing (S9). A library that writes a global on import surprises every bundler and module consumer, and Photonic's decoupling made the same cut, moving `window.Photonic` out of its library entry and into its demo host page. Fix approach: sever — D2 removes the assignment and fixes the header comment to describe the ES module surface; the package's only surface is its default and named exports. If a future demo or host page in this repo wants a `window.Sonance` global for script-tag use, that page sets it itself from the imported module, the same pattern Photonic adopted; no such page is D2 work, and X1's rebuilt examples will import the package properly instead of reading the global.

### S5 — The webpack entry and build layout: sever (the library needs no bundler)

The host's webpack config declares `sonance: './src/sonance/index.js'` as one of its entries and emits it as `sonance.gen.js` into `CodeCubeConsole/out/script`, processed by babel-loader with preset-env and preset-react (verified in `extraction-notes/webpack.config.js`). Nothing in the Sonance sources depends on webpack — the sources are native ES modules with full `.js` extensions throughout — but the bundle was the only way anything consumed Sonance, so the build layout acted as a coupling: no webpack, no Sonance. Fix approach: sever — D2 adds no build step and no bundler config; the library is consumed as the ES modules it already is, through the `package.json` entry E2 set (`main`, `module`, and `exports` all pointing at `./src/index.js`), with a consumer's own bundler or an import map resolving the one bare specifier, `tone`, exactly as the standalone test below demonstrates. The `sonance.gen.js` bundle name and the `CodeCubeConsole/out/script` output path remain the host site's business; if the site later consumes the decoupled package, that is consumer-flip work (roadmap C1), not something this repo ships. The webpack evidence copy stays in `extraction-notes/` as the record of how the host built it.

### S6 — The JSON soundtrack bundler assumption: sever the assumption, keep the data

`SoundtrackLoader.js` itself is clean — `loadSoundtrack(engine, definition, overrides)` takes a plain object and never imports the JSON file — but its header usage example (line 7) teaches `import trackDef from './soundtracks/ambient-demo.json'`, which only works where a bundler or a JSON-module-aware runtime resolves a `.json` import; a plain browser ES module import of that line fails, and Node requires an import attribute. The bundled demo soundtrack, `src/soundtracks/ambient-demo.json`, is itself host-free pure data and already ships inside the package's `files` set. Fix approach: sever the assumption in the documentation, not the data — D2 rewrites the header example to show the two standalone-safe ways to get the definition object: fetch and parse (`const trackDef = await fetch(new URL('./soundtracks/ambient-demo.json', import.meta.url)).then(r => r.json())` or any consumer-side file read), or a JSON import attribute (`import trackDef from './soundtracks/ambient-demo.json' with { type: 'json' }`) where the runtime supports it, and states plainly that `loadSoundtrack` only needs the parsed object. The standalone test loads the demo soundtrack the fetch-and-parse way, proving no bundler is involved.

### S7 — SonanceSceneManager's localStorage and DOM helpers: internalize (standard platform, already guarded; document the contract)

`SonanceSceneManager` stores named scenes in `localStorage` under the prefix `sonance-scene:` (save, load, list, delete) and offers two DOM helpers: `download`, which builds a Blob and clicks a temporary anchor element, and `upload`, which opens a file input and reads the chosen file with `FileReader`. Every one of these is a standard browser platform API, not host knowledge — there are no host URLs, element ids, or page assumptions anywhere in the file — and the guards are already in place: all four localStorage methods check `typeof localStorage === 'undefined'` first and no-op safely (load returns `null`, list returns `[]`), `download` returns early when `document` is undefined, and `upload` rejects with a clear "No document available" error in that case, so importing and even calling this class in Node does not crash. Fix approach: internalize as-is — D2 changes no behaviour in this file beyond the `applyScene` modulation skip specified in S2, and instead documents the contract in the README: scene storage and file helpers are optional browser conveniences that degrade safely outside a browser, and the core scene operations (`listPresets`, `getPreset`, `applyScene`, and definition validation) work anywhere. The standalone test exercises exactly that claim by listing presets and calling save and load in the Node tier, where they must no-op without throwing.

### S8 — The extracted tests' host import paths and missing test setup: sever the paths, internalize a minimal setup

Both tests import through the host's layout — `tests/MidiUtils.test.js` imports from `../src/sonance/MidiUtils.js` and `tests/VariationUtils.test.js` from `../src/sonance/variation.js` — paths that resolved inside `frontend/` but resolve nowhere here, where the files live at `../src/MidiUtils.js` and `../src/variation.js` relative to `tests/`. They were kept byte-identical in E1 on purpose; in this repo they have never run. The setup they ran under was also the host's: the host jest config (verified in `extraction-notes/jest.config.js`) used the jsdom environment, a babel-jest transform with the host's babel config (preset-env plus preset-react), and a `tests/setup.js` file that serves the whole host suite and was deliberately not extracted. Neither test needs any of that weight: both exercise pure functions (`MidiUtils` and `variation` have no imports and touch no DOM), the variation test supplies its own hand-written Tone mock, and both use only the standard jest globals (`describe`, `test`, `expect`, `jest.spyOn`). Fix approach: sever and internalize — D2 changes exactly the two import lines to the in-repo paths, adds jest as a devDependency at `^30.0.5` (the host's major version, verified in `extraction-notes/frontend-package.json`), and adds a minimal test setup owned by this repo: since `package.json` already declares `type: module` and the sources are native ES modules, jest runs in its ESM mode (`node --experimental-vm-modules` via the `test` script) with the `node` test environment and no transform at all — no babel, no preset-react, and no equivalent of the host's `tests/setup.js`, which goes on the unsupported list below as host infrastructure Sonance never needed. D2 adds the `test` script to `package.json` and the pass condition is simple: `npm test` runs both suites green in this repo. A lighter runner such as Node's built-in test runner was considered and rejected for D2 because the tests are written against the jest API (`jest.spyOn`, `jest.restoreAllMocks`); rewriting them would change extracted files beyond the import lines for no decoupling benefit.

### S9 — The host consumers (photonics examples): drop to the explicitly unsupported list until X1

The only consumers of Sonance in the host are `frontend/src/photonics/audio-demo.js` and `frontend/src/photonics/synth-designer.js`, the two Photonic examples parked as unsupported after Photonic's extraction. Both check for `window.Sonance` and build through `window.Sonance.createEngine()` and `window.Sonance.Tone`, synth-designer additionally imports `SonanceSceneManager` directly from `../sonance/SonanceSceneManager.js`, and both import helpers from `../modulation/index.js` directly as well. These files live in the host repo, not this one, and every assumption they make — the global (S4), the cross-tree paths (S2, S3), and a Modulation workstream this plan severs — is removed or changed by D2, so they cannot be part of D2's supported set and D2 does not edit them. Fix approach: drop to the explicitly unsupported list — the README's status section names both modules as not yet working against the standalone library, and roadmap item X1 is where they are rebuilt or adopted here as Sonance's own examples, importing `@codecube/sonance` as ES modules and passing a modulation system through the S2 injection seam if they still want one. Nothing about their current host-site behaviour changes: the host still builds its own bundle from its own copy of these sources, and this repo's decoupling does not reach back into the host (that flip is roadmap C1, after the publish gate).

## Explicitly unsupported list

D2's README status update states this list plainly, so the boundary of the standalone library is a documented fact rather than something a consumer discovers by failing: (1) built-in modulation — Sonance ships no `ModulationSystem`; modulation is available only by injecting a system through `options.modulation` (S2), and the nine host-era Modulation re-exports are gone (S3); (2) the `window.Sonance` script-tag consumption model and the host's `sonance.gen.js` webpack bundle as a way to consume this package (S4, S5); (3) the host photonics consumers `audio-demo.js` and `synth-designer.js` running against the standalone library, until X1 rebuilds them here (S9); (4) the host test infrastructure — the host's `tests/setup.js`, its babel and React preset stack, and the host jest config — none of which Sonance's own minimal setup replaces or needs (S8); and (5) `SonanceSceneManager.download` and `upload` outside a browser, which are DOM helpers by nature and degrade as documented in S7 rather than being supported in Node.

## Recommended D2 execution order

D2 executes in this order, and each step leaves the repo working: (1) S2 and S3 together, since they are the same cut seen from two files — remove the Modulation import from `SonanceEngine.js`, make the injected system optional with the defined no-system behaviour, apply the `applyScene` modulation skip in `SonanceSceneManager.js`, and strip the Modulation import, namespace, and re-exports from `src/index.js`; (2) S4, remove the `window.Sonance` assignment and fix the entry point's header comment; (3) S6, rewrite the `SoundtrackLoader.js` header example to the standalone-safe loading patterns; (4) S8, fix the two test import lines, add the jest devDependency and the `test` script, and get `npm test` green; (5) S1, S5, and S7 confirmations — no code changes, but verify the `tone` declaration, the entry-point fields, and the scene manager guards are exactly as this plan describes, and update the README status section to record the severed couplings and the unsupported list (S9 included); (6) run the standalone-consumption test below and record its evidence in PROGRESS.md. Steps 1–2 make the library importable, step 3 makes its own example honest, step 4 makes its tests real, step 5 makes the boundary documented, and step 6 proves the whole claim.

## Standalone-consumption test (the D2 proof)

The test lives in a fresh folder outside this repo — D2 creates it at `/tmp/sonance-standalone-test/` and deletes any previous copy first — and it mimics a real consumer using the peer-checkout convention from the Photonic path: the test folder contains a `sonance/` folder that is a plain copy of this repo with its `.git` folder removed, and beside it a `consumer/` folder whose only hand-written files are a `package.json`, an `index.html`, an `example.js`, and a small static-server script; no Static-Site-Generator file, no `modulation/` folder, and no webpack or babel config may exist anywhere in the test tree, and D2 verifies that by listing the full tree and grepping it for `modulation` and `sonance.gen` before running anything. The consumer's `package.json` declares exactly two things: `"@codecube/sonance": "file:../sonance"` as its only dependency and `"type": "module"`, and `npm install` inside `consumer/` is the only install step, so everything the example uses beyond Sonance itself — in practice `tone`, pulled in as Sonance's declared dependency — arrives from Sonance's own declarations alone.

The test then runs in two tiers, and both must pass. The Node tier runs a script inside `consumer/` that imports the package by name (`import Sonance, { SonanceEngine, SonanceSceneManager, MidiUtils, loadSoundtrack } from '@codecube/sonance'`) and asserts, in order: the import resolves with no missing-module or missing-export error; none of the nine severed Modulation names (`Modulation`, `ModulationSystem`, `Modulator`, `ModulationBinding`, `clamp`, `createPhotonicFrameContext`, `distance3D`, `lerp`, `normalizeToUnit`, `readPath`) is present on the imported surface; `new SonanceEngine()` constructs with no arguments and its `modulation` getter returns `null`; `MidiUtils.buildTimedEvents` on the sample sequence from `tests/MidiUtils.test.js` returns the timings that test expects; `SonanceSceneManager.listPresets()` returns the four built-in preset names, and `save` and `load` called in Node no-op safely (save does not throw, load returns `null`); the demo soundtrack file is read from the installed package and parsed with `JSON.parse` on a plain file read — no bundler, no JSON import — and the result is an object with a `channels` map; and calling `engine.createModulator('x', {})` throws the clear no-modulation-system error from S2, proving the failure mode is the designed one. The browser tier serves `consumer/` with the static server and loads `index.html` in a headless browser: the page carries an import map that resolves the bare `tone` specifier into the installed `node_modules`, and `example.js` imports `@codecube/sonance` from its installed location, creates an engine through `createEngine()`, applies the built-in `Ambient Drone` preset through `SonanceSceneManager.applyScene` (which must apply its soundtrack while warning that its modulators were skipped, per S2), fetches `ambient-demo.json` from the installed package and passes the parsed object to `loadSoundtrack`, and records each step's success on the page. The tier passes only if the headless check confirms every step recorded success, zero console errors, zero failed network requests, and `window.Sonance` is `undefined` — proving the library set no global (S4) and the page never needed one.

Two grep gates close the test, run over this repo rather than the test folder: no file under `src/` contains `../modulation`, `window.Sonance`, or `sonance.gen`; and `npm test` in this repo runs both extracted suites green under the S8 setup. D2 records the exact commands, the test-tree listing, and the tier outputs in PROGRESS.md as the D2 evidence. A failure on any single criterion is a D2 failure to fix in the implementation, not a test detail to be edited away; if a criterion turns out to be wrong about the library's intended behaviour, that is a plan change Joel hears about in a check-in before the test is touched.

## What D2 does not do

D2 does not publish anything, does not push to GitHub, does not extract the Modulation workstream, does not rebuild the photonics examples (X1), does not write type declarations or the final exports map beyond keeping the entry E2 set working (P1), and does not change any behaviour of the nine already-clean source files. The host site's own copy of Sonance and its consumers are untouched by all of this; the consumer flip is roadmap C1, after the publish gate.
